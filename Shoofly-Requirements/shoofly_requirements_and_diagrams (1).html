🔐 Authentication & identity
  • FR-01Register as Client, ManualServiceProvider, DigitalServiceProvider, or Coordinator with role-specific fields (bio, region, portfolio URL).Must
  • FR-02Login with JWT access token and sliding-window refresh token stored in UserRefreshToken table.Must
  • FR-03Revoke individual or all sessions; coordinator can revoke other users' sessions via Permissions.Security.Must
  • FR-04Multi-language preference (PreferredLanguage) stored per user; responses localised via SharedResources.Should
  • FR-05Admin can change user IsActive flag, manage roles and permission claims.Must
🗂️ Category & service catalogue
  • FR-06Browse top-level Categories (Manual / Technical). CategoryType drives which flow the client enters.Must
  • FR-07Manual path: SubCategory → ManualService list with pricing, cover photo, and RequiresTeam flag.Must
  • FR-08Technical path: SubCategory → list of DigitalServiceProvider profiles filtered by IsAvailable and AverageRating.Must
  • FR-09Admin seeds categories, sub-categories, and manual services; digital providers self-register under SubCategories.Must
🛒 Manual (Talabat-style) order flow
  • FR-10Client adds ManualServices to Cart; each CartItem records AddedDate for stale-item cleanup.Must
  • FR-11Client checks out: provides service address, ServeDate, notes, and PaymentMethod to create one Order with multiple OrderItems.Must
  • FR-12Coordinator reviews Order, sets CoordinatorId, then triggers dispatch per OrderItem.Must
  • FR-13Smart dispatch: system selects ManualServiceProvider matching Region + OfferedServices + IsAvailable, creates DispatchAttempt (Status=Sent), and pushes a notification.Must
  • FR-14Provider accepts → DispatchAttempt=Accepted, OrderItem.ProviderId set, ItemStatus=Assigned, provider IsAvailable=false.Must
  • FR-15Provider declines or timeout expires → DispatchAttempt=Declined/Expired, system picks next candidate and repeats.Must
  • FR-16If ManualService.RequiresTeam=true, Coordinator assigns a ManualTeam instead of a solo provider to that OrderItem.Must
  • FR-17OrderItem status lifecycle: Pending → Dispatching → Assigned → InProgress → Completed → Review created.Must
  • FR-18Master Order status rolls up from its items: all Completed → Order Completed; any Cancelled → adjusts accordingly.Should
💻 Digital (Khamsat-style) order flow
  • FR-19Client browses DigitalServiceProvider profiles, views PortfolioUrl, AverageRating, HourlyRate, IsVerified badge.Must
  • FR-20Client places DigitalOrder directly on a provider or DigitalTeam: title, description, agreed price, delivery days.Must
  • FR-21Provider accepts or declines DigitalOrder; on acceptance Status transitions to Accepted → InProgress.Must
  • FR-22Provider uploads DeliverableUrl; order moves to UnderReview; client approves → Completed or raises dispute → Disputed.Must
  • FR-23No cart for digital orders — direct order placement only.Must
⭐ Reviews & ratings
  • FR-24Client submits Review (1–5 stars + comment) per OrderItem after ItemStatus=Completed; Review is tied to the specific task, not the whole order.Must
  • FR-25Client submits DigitalReview per DigitalOrder after Status=Completed.Must
  • FR-26ManualServiceProvider.AverageRating and DigitalServiceProvider.AverageRating are recalculated and cached after each new review.Should
🔔 Notifications
  • FR-27Push/in-app Notification sent for: dispatch requests, order status changes (manual + digital), payments, and general admin messages.Must
  • FR-28NotificationType field tells the mobile app how to route the tap: DispatchRequest opens accept/decline screen; OrderUpdate opens order detail.Must
  • FR-29Unread notifications count shown in-app; mark individual or all as read.Should
💰 Transactions & financials
  • FR-30Transaction recorded for: ClientPayment, ProviderEarnings, DigitalProviderEarnings, PlatformCommission, Refund, Withdrawal, SalaryPayment.Must
  • FR-31Wallet balance derived from Transaction ledger per user (sum of positive minus negative amounts).Should
  • FR-32Provider can request withdrawal to bank / Vodafone Cash; coordinator approves and records Transaction.Could
👥 Teams
  • FR-33Admin/Coordinator creates ManualTeam, assigns ManualServiceProvider members and QualifiedServices.Must
  • FR-34DigitalServiceProvider creates/joins DigitalTeam; each member keeps their own profile and rating.Must
  • FR-35Client can place DigitalOrder targeting a DigitalTeam rather than an individual provider.Should

⚡ Performance
  • NFR-01API response time ≤ 300 ms at p95 under 500 concurrent users for catalogue and order endpoints.perf
  • NFR-02AverageRating cached on provider record; never computed in real-time per request to avoid N+1 joins.perf
  • NFR-03Dispatch algorithm must resolve a candidate provider within 2 seconds of Coordinator triggering dispatch.perf
  • NFR-04Push notifications delivered within 5 seconds of the triggering event (order placed, dispatch attempt, status change).perf
🔒 Security
  • NFR-05All endpoints protected with JWT bearer auth; role-based authorization enforced via ASP.NET Identity claims.security
  • NFR-06Refresh tokens hashed in storage, single-use (IsUsed flag), with expiry enforced server-side.security
  • NFR-07Admin-only permission claims (Permissions.Security.RevokeSessions) enforced at action level.security
  • NFR-08Sensitive fields (document URLs, salary) readable only by the owner or Admin/Coordinator roles.security
  • NFR-09All API communication over HTTPS/TLS 1.2+; no sensitive data in query strings or logs.security
🛡️ Reliability & availability
  • NFR-10DispatchAttempt table provides full audit trail; no dispatch state is held only in memory — system restarts safely re-query pending attempts.reliability
  • NFR-11Transaction ledger append-only; no record is ever deleted — refunds and corrections are new Transaction rows.reliability
  • NFR-1299.5% uptime SLA for production; database daily backups with point-in-time recovery.reliability
📈 Scalability
  • NFR-13Dispatch query uses indexed Region + ManualService + IsAvailable columns to avoid full-table scans as provider count grows.scalability
  • NFR-14Architecture supports horizontal scaling of the API layer behind a load balancer; JWT is stateless.scalability
  • NFR-15Notification delivery extracted to a background job / message queue so it doesn't block the HTTP request thread.scalability
🌍 Usability & internationalisation
  • NFR-16All user-facing strings in SharedResources; Arabic (ar) and English (en) supported from day one.usability
  • NFR-17Country.DialCode stored for all phone numbers; international format enforced on registration.usability
  • NFR-18Decimal amounts stored as decimal(18,2) to avoid floating-point rounding in financial records.usability
🧱 Maintainability
  • NFR-19Clean Architecture layers: Data → Shared → Infrastructure → Core → API; no upward dependencies.maintainability
  • NFR-20All enum values stored as strings in the DB (HasConversion<string>) for readability in SQL queries and migrations.maintainability
  • NFR-21Seeders are idempotent (AnyAsync guard) and run on every startup — safe to re-run in CI/CD pipelines.maintainability
